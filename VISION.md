# Vision & Product Contract

## Problem
Engineering work is fragmented across chats, agents, IDE sessions, project repos, tool-specific skills and disconnected test logs. Capabilities are rediscovered, verified failures are forgotten, and upstream knowledge is rarely shared. A project may be functionally correct yet visually unpolished, or impressive in a screenshot but unsafe in data handling.

## Product outcome
EngineeringOS makes a reusable operating method portable across programming languages and projects. The system can: (1) discover and prepare an environment; (2) select and coordinate domain experts; (3) create and evaluate varied technical and creative alternatives; (4) enforce evidence/approval gates; (5) archive traceable lessons, tool outcomes and anti-patterns; (6) submit sanitized public contributions; and (7) evolve without silent upgrades.

## Coverage (not limited to UI)
Frontend and interactive UX, visual direction/animation/themes, backend/service design, APIs/contracts, domain/data models, SQL/databases/migrations, systems architecture, security/privacy, CI/CD, native platform QA, performance, docs, release operations and product decision support.

## Human authority
The project owner determines product goals, scope, data egress, integration and release permissions. An AI role is not automatically a different model instance, and three skills in a single context are not three independent reviewers. Evidence, model provenance, observed tests and human acceptance must remain distinguishable.

## Public adoption principles
Works with a simple static README and CLI before any orchestrator; does not mandate cloud accounts or always-on memory. Users can select offline-only profiles. Supports new harnesses/models via adapters, not copy-pasted core policy. No requirement that every tool be installed or used on every task.

## Success examples
- An existing .NET service gets its relevant project kit without losing its own repo governance.
- Two design specialists generate distinct visual directions; a third independently reviews accessibility; QA checks keyboard, motion and mobile; PO chooses the final direction.
- A SQLite migration failure produces a reproducible, sanitized test and a reviewer-approved lesson, reusable in a separate project.
- A new Claude harness can be added as a versioned capability proposal without changing existing Codex project configurations.
