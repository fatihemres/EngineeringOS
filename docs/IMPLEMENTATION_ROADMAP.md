# EngineeringOS proposed delivery increments (not approved milestones)

| Phase | Outcome | Testable acceptance target |
| --- | --- | --- |
| E0 Foundations | Public/private contract, repo governance, initial source pack | Independent reader understands boundaries; owner approves license and repo controls |
| E1 Bootstrap | Project doctor, profile validator, ChatGPT kit and safe setup planner | Existing project detected without overwrite; dry-run and idempotence tests |
| E2 Registry | Versioned capabilities/compatibility/lifecycle, license/trust review | Candidate can be added, vetted, deactivated and pinned |
| E3 Orchestration | Agent-independent option/critique/synthesis handoffs | Distinct agent identities, source/evidence, bounded disagreement, owner approval |
| E4 Experience Ledger | Schema, local private store, sanctioned public promotion | Negative/positive case retrievable with provenance; private data not leaked |
| E5 Contribution Gateway | Proposal from project to EngineeringOS Issue/PR/CI | Synthetic lesson passes review; rejection and conflicts preserved |
| E6 Distribution | Multi-project adapters, versioned updates and rollback | Two different stack pilots; reproducible project setup and update |
| E7 UI/observability (optional) | Inspectable workflows, agent outcomes, tool changes | Useful human audit trail; no hidden telemetry |

All phases must cross separate PO permission checkpoints for implementation, integrations and public release. E0 draft construction in this conversation is not itself such an approval for hosted repo changes.
